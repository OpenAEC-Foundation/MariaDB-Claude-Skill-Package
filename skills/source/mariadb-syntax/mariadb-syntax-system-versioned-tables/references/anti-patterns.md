# Anti-Patterns : System-Versioned Tables and Application-Time Periods

Ten real-world traps with the failure mode and the correct alternative. Verified against `mariadb.com/kb/en/system-versioned-tables/`, `mariadb.com/kb/en/application-time-periods/`, and `mariadb.com/kb/en/bitemporal-tables/` on 2026-05-19.

## 1. System-versioned table without HISTORY PARTITION

**Anti-pattern :**

```sql
-- BAD : unbounded history growth, current-row scans degrade over time
CREATE TABLE audit_log (
  event_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  payload  TEXT
) WITH SYSTEM VERSIONING;
```

**Why it fails :** History rows are appended to the same physical structure as current rows. A heavily-updated table accumulates millions of dead versions ; current-row scans become history-scans. There is no built-in retention without `DELETE HISTORY` calls.

**Correct alternative :**

```sql
-- GOOD : 10.9.1+ auto-rotating, separable history
CREATE TABLE audit_log (
  event_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  payload  TEXT,
  row_start TIMESTAMP(6) GENERATED ALWAYS AS ROW START,
  row_end   TIMESTAMP(6) GENERATED ALWAYS AS ROW END,
  PERIOD FOR SYSTEM_TIME (row_start, row_end)
) WITH SYSTEM VERSIONING
  PARTITION BY SYSTEM_TIME INTERVAL 1 MONTH AUTO;
```

Pre-10.9.1, declare explicit partitions and rotate manually with `ALTER TABLE ... DROP PARTITION`.

## 2. Confusing system-time with application-time

**Anti-pattern :**

```sql
-- BAD : trying to model "the contract is valid during 2026"
-- by inserting a row with row_start = '2026-01-01' (impossible)
INSERT INTO contracts (id, terms, row_start)
  VALUES (1, 'standard', '2026-01-01');
-- ERROR : cannot write generated column
```

**Why it fails :** `row_start` and `row_end` mean "when was this row written to the database", not "when does this contract apply in the real world". They are generated by the server and not writable.

**Correct alternative :**

```sql
-- GOOD : use application-time period for business validity
CREATE TABLE contracts (
  id INT, terms TEXT,
  valid_from DATE NOT NULL, valid_to DATE NOT NULL,
  PERIOD FOR validity (valid_from, valid_to)
);
INSERT INTO contracts VALUES (1, 'standard', '2026-01-01', '2026-12-31');
```

For audited contracts (both dimensions), use a bitemporal table (10.5+).

## 3. Querying with FOR SYSTEM_TIME AS OF NOW() "to be safe"

**Anti-pattern :**

```sql
-- BAD : pointless and slower
SELECT * FROM accounts FOR SYSTEM_TIME AS OF NOW();
```

**Why it fails :** Plain `SELECT` already returns the current row state. Adding `FOR SYSTEM_TIME AS OF NOW()` triggers the temporal access path and may inhibit some optimizations. It is also redundant noise that obscures intent.

**Correct alternative :**

```sql
-- GOOD
SELECT * FROM accounts;
```

Use `FOR SYSTEM_TIME` only when you actually want history.

## 4. Using FOR PORTION OF on system_time

**Anti-pattern :**

```sql
-- BAD : raises a syntax error on bitemporal tables
DELETE FROM contracts
  FOR PORTION OF system_time FROM '2026-01-01' TO '2026-02-01';
```

**Why it fails :** `FOR PORTION OF` is exclusively for application-time periods. The system-time period is server-controlled and cannot be sliced. The KB explicitly forbids this.

**Correct alternative :**

```sql
-- GOOD : DELETE HISTORY purges system-time history
DELETE HISTORY FROM contracts BEFORE SYSTEM_TIME '2026-02-01';

-- or for application-time slicing
DELETE FROM contracts
  FOR PORTION OF application_time FROM '2026-01-01' TO '2026-02-01';
```

## 5. Expecting CASCADE history-purge on FK delete

**Anti-pattern :**

```sql
-- BAD : assuming history of child rows disappears when parent row is deleted
DELETE FROM parents WHERE id = 1;
-- expects children's history to vanish ; it does NOT
```

**Why it fails :** `ON DELETE CASCADE` cascades the current-row deletion. The child table's history retains both the now-deleted current row and all prior versions. Foreign-key cascades are orthogonal to system-versioning.

**Correct alternative :**

```sql
-- GOOD : purge child history explicitly
DELETE FROM parents WHERE id = 1;
DELETE HISTORY FROM children WHERE parent_id = 1;
```

For GDPR right-to-be-forgotten, always combine the current-row delete with an explicit history purge.

## 6. Forgetting DELETE HISTORY for GDPR compliance

**Anti-pattern :**

```sql
-- BAD : "I deleted the user's row, we are GDPR-compliant"
DELETE FROM users WHERE id = 42;
```

**Why it fails :** The user's prior versions still exist in history rows. A subsequent `SELECT ... FOR SYSTEM_TIME ALL` reveals every previous version, including the email and other personal data the user asked to erase.

**Correct alternative :**

```sql
-- GOOD : remove the current row AND all history
DELETE FROM users WHERE id = 42;
DELETE HISTORY FROM users WHERE id = 42;
```

Grant the application's compliance role the `DELETE HISTORY` privilege explicitly.

## 7. Trying to TRUNCATE a versioned table

**Anti-pattern :**

```sql
-- BAD
TRUNCATE TABLE accounts;
-- ERROR 4137 : Truncate is not allowed on system-versioned table
```

**Why it fails :** TRUNCATE would discard history, which the SQL:2011 contract forbids without explicit `DELETE HISTORY`.

**Correct alternative :**

```sql
-- GOOD : wipe current and history separately
DELETE FROM accounts;
DELETE HISTORY FROM accounts;

-- or drop and recreate when wiping is mandatory
DROP TABLE accounts;
CREATE TABLE accounts (...) WITH SYSTEM VERSIONING ...;
```

## 8. Dropping row_start or row_end directly

**Anti-pattern :**

```sql
-- BAD : the server refuses
ALTER TABLE accounts DROP COLUMN row_start;
```

**Why it fails :** Period columns are managed by the system-versioning machinery. Dropping them outside that machinery leaves the table in an invalid state.

**Correct alternative :**

```sql
-- GOOD : drop versioning first, then the columns and PERIOD
ALTER TABLE accounts DROP SYSTEM VERSIONING;
ALTER TABLE accounts
  DROP PERIOD FOR SYSTEM_TIME,
  DROP COLUMN row_start,
  DROP COLUMN row_end;
```

## 9. Switching precision after the table is populated

**Anti-pattern :**

```sql
-- BAD : trying to change BIGINT UNSIGNED (transaction-id) to TIMESTAMP(6) in place
ALTER TABLE accounts MODIFY row_start TIMESTAMP(6) GENERATED ALWAYS AS ROW START;
-- transaction-ids cannot be converted to wall-clock times after the fact
```

**Why it fails :** The historic transaction-ids do not carry the timestamps when they were committed. There is no lossless conversion.

**Correct alternative :**

```sql
-- GOOD : decide precision at CREATE time. To migrate, copy data forward.
CREATE TABLE accounts_new (
  id INT PRIMARY KEY,
  balance DECIMAL(15,2),
  row_start TIMESTAMP(6) GENERATED ALWAYS AS ROW START,
  row_end   TIMESTAMP(6) GENERATED ALWAYS AS ROW END,
  PERIOD FOR SYSTEM_TIME (row_start, row_end)
) WITH SYSTEM VERSIONING;
INSERT INTO accounts_new (id, balance)
  SELECT id, balance FROM accounts FOR SYSTEM_TIME ALL;
RENAME TABLE accounts TO accounts_old, accounts_new TO accounts;
```

History from the old table cannot be reconstructed with wall-clock precision ; accept the loss and start over.

## 10. ALTER TABLE on a versioned table without setting system_versioning_alter_history

**Anti-pattern :**

```sql
-- BAD : default behaviour rejects ALTER
ALTER TABLE accounts ADD COLUMN currency CHAR(3);
-- ERROR : Not allowed for system-versioned `accounts`
```

**Why it fails :** `system_versioning_alter_history` defaults to `ERROR`. The server protects history-accuracy by refusing schema changes that would make historic rows ambiguous.

**Correct alternative :**

```sql
-- GOOD : opt in to the trade-off explicitly
SET SESSION system_versioning_alter_history = KEEP;
ALTER TABLE accounts ADD COLUMN currency CHAR(3);
SET SESSION system_versioning_alter_history = DEFAULT;
```

After this, history rows carry `currency = NULL` (or the default). NEVER pretend the historic value is meaningful ; document the schema change as a discontinuity.

## 11. FOR SYSTEM_TIME on a non-versioned table

**Anti-pattern :**

```sql
-- BAD : table was never WITH SYSTEM VERSIONING
SELECT * FROM legacy_table FOR SYSTEM_TIME AS OF '2026-01-01';
-- ER_VERS_NOT_VERSIONED
```

**Why it fails :** `FOR SYSTEM_TIME` requires the table to declare `WITH SYSTEM VERSIONING`. There is no implicit history on regular tables.

**Correct alternative :**

```sql
-- GOOD : decide between adding versioning forward or hand-rolling
ALTER TABLE legacy_table ADD SYSTEM VERSIONING;
-- from now on, history accrues ; historic rows from before this point do NOT exist
```

You cannot retroactively backfill system-time history for rows that pre-date the versioning declaration.

## 12. Using PARTITION BY SYSTEM_TIME on a transaction-precision table

**Anti-pattern :**

```sql
-- BAD : default precision is transaction-id, partitioning fails
CREATE TABLE audit_log (
  event_id BIGINT PRIMARY KEY,
  payload  TEXT
) WITH SYSTEM VERSIONING
  PARTITION BY SYSTEM_TIME INTERVAL 1 MONTH;
-- ER_PARTITION_DEFAULT_ERROR
```

**Why it fails :** `PARTITION BY SYSTEM_TIME` requires timestamp-precision period columns. Transaction-id columns have no wall-clock value to bucket on.

**Correct alternative :**

```sql
-- GOOD : declare TIMESTAMP(6) period columns
CREATE TABLE audit_log (
  event_id BIGINT PRIMARY KEY,
  payload  TEXT,
  row_start TIMESTAMP(6) GENERATED ALWAYS AS ROW START,
  row_end   TIMESTAMP(6) GENERATED ALWAYS AS ROW END,
  PERIOD FOR SYSTEM_TIME (row_start, row_end)
) WITH SYSTEM VERSIONING
  PARTITION BY SYSTEM_TIME INTERVAL 1 MONTH;
```

If you must keep transaction precision, drop the partition clause and use `DELETE HISTORY` for retention.
